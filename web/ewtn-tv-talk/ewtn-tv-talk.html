EWTN+ for TV

A streaming app for three platforms with a single codebase

How we built the EWTN+ TV app with React Native, what broke along the way, and how we fixed it. Written for the whole team: no React Native or TV experience assumed.

01 The client

EWTN: a global Catholic media network with a TV app to replace

EWTN runs television, radio, news, and digital platforms. Founded in 1981 in Alabama, it broadcasts 24/7 in several languages to audiences around the world. An established brand with a large, global audience.

Their legacy TV app covered fewer use cases. Instead of extending it, they decided to build a new one from scratch, with feature parity across platforms and accessibility as a requirement.

Three stores means three review processes, three artifact formats, and three device families.

What EWTN+ ships

  • Global live channels

  • The Bible
  • Profiles and My List

02 The bet

One codebase, three stores

React Native on the react-native-tvos fork, plus Expo, in TypeScript. Every platform wants a different build format, different asset formats, and a different process. The same code produces all of them, and EAS runs the builds and submissions in the cloud.

One codebase React Native tvOS + Expo, TypeScript
EAS Build Cloud builds and store submissions
  • .ipa Apple App StoretvOS, via TestFlight
  • .aab Google PlayAndroid TV, Google TV
  • .aab / .apk Amazon AppstoreFire TV, Amazon variant

Why React Native

A single UI and a single team, prior React experience, and a fork that adds tvOS and Android TV support on top of React Native. The client chose the technology, expecting to reuse code with the mobile app and even the .com site; shared folders were structured with that in mind. The alternative, two or three native teams with three codebases, was ruled out by client decision.

What changes per platform

  • Four Android package identifiers (production and staging, Play and Amazon) and one iOS bundle, all from the same tree, resolved through environment variables when the config is evaluated.
  • Google Play requires an App Bundle. Amazon accepts .apk and .aab: here staging ships .apk and production .aab.
  • The Amazon variant isn't a Gradle flavor. An environment variable changes the package identifier and adds the banner Fire TV's launcher requires.
  • Native divergences go through Expo config plugins, so there are no hand-maintained android/ and ios/ folders.

03 Challenges

Where the cost went

Navigation, data, and state were solved as in any React Native app. The project's cost concentrated in what is specific to TV and to this stack. Five challenges, in order of cost.

  1. Focus No pointer or touch on TV. The remote's D-pad moves focus, and each OS's native engine decides where it lands. They behave differently. Highest cost of the project
  2. A single codebase for three platforms tvOS and Android differ in event order and focus behavior. A fix for one often broke the other.
  3. Screen readers VoiceOver and TalkBack double the test matrix and fail in opposite ways.
  4. Lack of documentation Far less material on TV apps than on mobile or web, on top of a fork that is little known and thinly maintained.
  5. Emulators vs physical devices Focus, accessibility, and performance behave differently on real hardware.

These challenges exist in any TV app. One codebase made them harder: solving a problem on one platform could open a new one on another.

1

Focus

On TV there is no pointer or touch: focus moves with the remote's D-pad. Where it lands is decided by each OS's native engine, UIKit on tvOS and FocusFinder on Android, based on the layout's geometry.

Mental model: on web or mobile the user points. On TV the system computes the most reasonable neighbor in the pressed direction.

The decision

Trust the native engine, supported by TVFocusGuideView (a react-native-tvos API) to bridge and contain regions. Complex designs, a hero with overlays, a collapsible side menu, grids inside rows, are exactly where geometry gets ambiguous.

Recurring symptoms

  • Focus escaping to the side menu during transitions
  • Focus lost after asynchronous loads
  • Initial focus on the wrong element
  • Screens with no focusable element
  • Overlapping elements

What we did, least invasive tool first

  • A focusable placeholder during loading states
  • Imperative focus with retries
  • Locking the side menu during navigation

The side menu was the big focus magnet: any instant without a focusable element on screen ended with the menu open. Some react-native-tvos APIs were poorly documented and only worked on one of the platforms.

2

A single codebase for three platforms

The react-native-tvos APIs were supposed to unify focus handling across platforms. Some were poorly documented or only worked on one of them, and the platforms handle focus and its events differently.

How each platform handles focus and reads the screen
Aspect tvOS (Apple TV) Android TV / Google TV Fire TV
Focus engine Infers targets by position and alignment. Supports diagonals and swipe. Looks for the closest element in the pressed direction (up, down, left, right). No diagonals. Same as Android
Event order The expected one: blur of the previous element, then focus of the new one. Focus of the new element before blur of the previous one. Same as Android
Screen reader VoiceOver TalkBack VoiceView

Proximity vs alignment: tvOS weights edge alignment heavily, Android looks for the closest neighbor in the direction. The same layout can be correct on one and ambiguous on the other.

Consequence of one codebase: fixing one platform was prone to breaking another. The UI carries many platform-conditional branches to apply different solutions.

3

Screen readers

On TV, accessibility focus can differ from interaction focus: the reader announces whatever holds accessibility focus. Every screen is validated on three platforms, with the reader on and off.

Android + TalkBack

TVFocusGuideView becomes an accessibility node and captures focus. It has to be replaced with a flat container, and the focus traps it provided have to be rewired by hand. To keep TalkBack from skipping virtualized items they stay mounted, at a performance cost.

tvOS + VoiceOver

Doesn't announce when focus is moved programmatically. Explicit announcements are required, with delays calibrated per screen, and the reading gets cut off if it coincides with UI updates. The pacing lever is the punctuation in the labels.

What we did

  • Reader state lives in the focus context
  • Accessible container and Android-specific focus guards
  • PR policy: four evidence videos per change, Apple and Android with the reader on and off

The two platforms fail in opposite ways. Android needs the component that makes focus work removed; tvOS needs the app to speak when the system stays silent. The four-videos-per-PR policy was the most effective measure against regressions.

4

Lack of documentation

react-native-tvos is a fork maintained by few people, with scarce documentation. TV support in Expo is experimental: it depends on an environment variable and a config plugin. With this stack, the library's source code is the documentation.

Gaps covered with our own engineering

  • react-native-video doesn't report bitrate changes on tvOS or in audio-only streams. We wrote native modules in Swift and Kotlin and inject them with config plugins.
  • Local storage on tvOS can be purged by the system. Session tokens live with that risk.
  • Expo dev builds need the mobile launcher intent, which a TV app shouldn't declare. The plugin removes it only in release.

Method

Read the libraries' source, isolate each divergence in a defensive config plugin (seven today), and document in the repo what upstream doesn't: a README of about 600 lines plus per-topic guides. Config plugins are regenerated on every build; if the file they expect has changed, they fail with a warning instead of an error.

Hidden cost of one codebase: we still had to write Swift and Kotlin. Less than in pure native, but not zero.

5

Emulators vs physical devices

Emulators are for developing, not for validating. Everything involving focus, screen readers, or performance gets decided on hardware.

What only showed up on hardware

  • Apple TV HD (1080p) showed a green vertical line and image rendering errors the simulator never reproduced. A per-model bug, invisible on Apple TV 4K.
  • Apple TV's VoiceOver can only be tested on a physical device.
  • Fire TV has no official emulator. Testing runs over adb against physical sticks and in a shared remote lab, and VoiceView is hardware only.
  • Between the Android TV emulator and a real Google TV, focus timing and the system keyboard behave differently.
  • D-pad lag and navigation delays appear only on real devices. Fire TV sticks are the most limited hardware and the one that exposes performance problems best.

Practice adopted

  • At least one physical device per platform from the start
  • Video evidence per PR

04 Assessment

React Native tvOS + Expo: what worked and what it cost

What worked

  • One codebase and a single UI for three stores.
  • Expo Router for navigation and EAS for builds and submissions: no local Xcode or Gradle.
  • Config plugins express native divergences without maintaining android/ and ios/ folders.
  • A usable React Native ecosystem (player, state, validation) and fast iteration with hot reload.

What it cost

  • The fork lags behind React Native and Expo. TV support is fragile.
  • Scarce documentation: the libraries' source code is the reference.
  • The native focus engine has no JS abstraction, which forces platform conditionals throughout the UI.
  • End-to-end testing is complex, with no mature tooling for TV.

Still positive for this client

Three stores with a small team would not have been viable in pure native. The cost concentrated in focus and accessibility; the rest of the app (navigation, data, state) was as productive as on mobile. Freezing dependencies was a deliberate call to stabilize. The upgrade debt exists and has to be planned for.

05 Alternatives

What else could have been on the table

The decisive constraint is tvOS: it rules out web, Flutter, and Kotlin Multiplatform for the App Store. Within the same stack, a JS spatial-navigation library is the most interesting option. It removes the differences between focus engines, but shifts accessibility onto the app. With designs full of overlapping elements, it deserves a proof of concept before deciding.

Alternatives to React Native tvOS + Expo, with their trade-offs
Alternative Pros Cons
Pure native (SwiftUI/UIKit + Compose for TV / Leanback) Better focus and accessibility. First-party APIs. Two codebases and two teams. Costly feature parity.
Flutter One codebase. Good rendering performance. No official tvOS target. TV focus handled manually.
Kotlin / Compose Multiplatform Shares logic with Android. No tvOS.
Web for TV (Lightning.js, Solid, Vue) One codebase for Smart TV, Fire TV web, and consoles. tvOS does not expose a WebView for App Store apps.
React Native + react-tv-space-navigation Focus is computed in JS and behaves the same on every platform. Gives up native focus and part of the system's accessibility.
Other decisions within React Native FlashList instead of FlatList. Bare React Native tvOS instead of Expo. More control in exchange for more maintenance.

Reference used for an internal self-audit: Callstack and Amazon's guide to TV development with React Native, 2026 edition. It came out a couple of months after we shipped to production. Many of the problems it lists are the ones we ran into, and solved.

06 Takeaways

Three things to take home

  1. One app, three stores, a small team. The bet works, with the cost concentrated in focus and accessibility.

  2. The native focus engine and screen readers are the real TV problem. The rest is conventional React Native development.

  3. What upstream doesn't document, the team documents. In code and in guides.
